# 阶段 11～20：Agent 研究能力与平台扩展计划

日期：2026-10-28。性质：设计与 Cursor 开发交接，**本文所列新能力均未实现／未验收**。阶段编号沿用用户参考，开发顺序按工程依赖调整。progress 的轮次编号与阶段编号无关。

## 1. 要做成什么

把项目从“可复现地运行和比较 Agent”推进到“能解释失败、构造可验证的故障任务、检验 Harness 改进是否有效”的实验平台。

核心研究问题：**在同一任务分布与明确的推理预算政策下，改变模型、Harness 或工具反馈，各自带来多少成功率、token 与耗时变化？改进能否迁移到未参与调优的任务家族？**

推荐主线：**13 失败诊断 → 18 离线回归门禁 → 16 故障注入 → 19 Docker SRE → 11 受约束任务生成 → 12 受控 Harness 优化**。14／15 先做协议设计，17／20 随真实规模推进。18 提前做，因为后续改动都需要可复用的回归门禁。

用户的 Cursor 开发额度将在十一月中旬到期。下文暂按 **2026-11-15 前收口** 排期，不假设具体截止日或剩余额度。额度用于实现、测试、评审、文档；Harness 的模型推理使用独立端点与独立预算。真实实验缺条件时，交付可运行的软件与明确的待验收清单，不伪造实验结论。

## 2. 当前起点与保留边界

已读路线图、后续双线计划、首次试运行计划及主要接口。当前具备：

- `Task`／`Solver`／`Scorer`／`SubmissionScorer` 插件，按样本 Docker 沙箱；SWE 的 submission 可在全新环境复核。
- `SampleResult` 保存 outcome、error_kind、messages、steps、artifacts、沙箱身份与调用统计；`Step` 保存工具调用、观察、完整输出引用、退出码、用量与耗时。
- `report` 已能按 outcome 抽样展示失败；`diff`／`compare` 已有配对比较、重复运行、环境漂移与可比性检查。
- Judge、onboarding、预算与消融最小实现已有代码。真实模型对照、真实消融、Judge 校准与真实自动接入仍需实际验证。
- 2026-10-28 本机完成三个自建终端任务 Oracle 3/3、不操作全失败、两个 Docker 正反例测试通过。不能据此推定 TB／SWE 或新 SRE 任务已验收。

这不是从参考文字所称“第五阶段只完成两小步”重新起步。继续复用现有能力，也不把阶段八“生成数据集适配器”误当成阶段十一“生成新题和独立验证器”。

三个逻辑层保持单仓库、单 Python 工程：

| 层 | 职责 | 本轮主要落点 |
|---|---|---|
| Evaluation Platform | 任务版本、环境、执行、判分、原始记录 | 现有 `core/`、`sandbox/`、`tasks/`；必要接口变更单独评审 |
| Agent Harness | 决策、工具、上下文、结束与恢复策略 | 现有 `solvers/`；研究实验中作为被测对象 |
| Research Layer | 诊断、回归策略、任务候选生成、配置搜索、统计报告 | 优先扩展 `analysis/`；新增 `research/` 容纳生成与优化 |

原始 manifest／JSONL／artifacts 是事实来源。诊断和回归输出写入独立目录，不能覆盖原始记录；SQLite 只能是可重建索引。暂不引入微服务、Rust 重写或 Kubernetes 调度控制面。

## 4. 首批开发任务：可单独评审的 PR 队列

所有命令名均为**待实现设计**，不是当前可运行命令。Cursor 实现后需同步 CLI help 与使用文档。建议每个 PR 聚焦一个用户行为，接口补充与大功能分开。

### PR-A：阶段 13，离线诊断最小版（立即开工）

目标：运行一次诊断，能看到失败样本有哪些可观察现象，以及支持判断的具体步骤。

建议落点：`src/harness/analysis/diagnose.py`、`tests/test_diagnose.py`；CLI 仅增加薄入口。输入通过现有 `read_results` 与 manifest 读取，不新增 runner 事件系统。

拟定入口：`harness diagnose RUN_DIR --output ANALYSIS_DIR`。默认纯离线，不实例化 Model、不创建容器、不执行日志中的命令。输出 `diagnosis.json` 和 `diagnosis.md`，包括：

- `schema_version`、分析器版本／参数指纹、输入文件哈希、run_id、task、sample_id、epoch。
- 原始 outcome／error_kind 与诊断 findings 分开；正确样本也可出现低效迹象，不能因此改判失败。
- 每个 finding：`label`、`rule_id`、`evidence`（step.index、tool_call_id、字段位置）、简短解释、证据等级；模型猜测另存，不与规则事实混用。
- `unknown`／`insufficient_trace` 与缺失信息说明；覆盖率、各标签数量与多标签共现，不强行互斥。

首版规则建议：完全相同工具名与规范化 JSON 参数连续重复达到阈值；同一命令连续非零退出；无工具调用终止且未解题；达到 step／time／token 上限；观察被截断且有完整输出引用；已有 env／API／scorer／solver 错误的来源呈现。

准确命名为 `repeated_tool_call`、`repeated_nonzero_exit`、`observation_truncated` 等“现象”，不叫“无效循环”“上下文遗忘”或“错误策略”。相同命令可能是合理轮询；截断可能无关最终失败。阈值、允许的参数规范化和例外写入分析配置，不改命令空白或 shell 语义来做过度归并。

验收用例：相同调用与不同调用、合理轮询也只报现象、成功但重复、不同 epoch、不完整工具记录、无 steps 的普通问答、env_error 不归成推理失败、缺失 artifact／不安全路径、报告转义、损坏 JSONL 明确报错且不写成功报告。冻结小型旧格式 fixture 验证兼容；同输入输出稳定；原始归档运行前后哈希不变。预留人工标签文件以便后续报告精确率／覆盖率，先不宣称智能诊断准确率。

明确不做：LLM 自动根因裁决、向量数据库、工具调用图平台、自动修改 prompt。

### PR-B：阶段 18，离线回归策略（紧随 A）

目标：已有两次运行可进入机器可判定的回归检查，用于后续每项功能的门禁。

建议落点：`analysis/regression.py`、`tests/test_regression.py`、`configs/regression-policy-example.yaml`。复用 `diff.py`／`compare.py`／`stats.py`／`environment.py`，不要重写统计口径。

拟定入口：`harness regression BASELINE CANDIDATE --policy POLICY --output DIR`。策略记录固定数据版本、匹配键、允许变化字段、配对评分指标、最小样本量、退化容忍值、环境错误率与成本门槛。匹配使用 task＋sample_id＋epoch，不能只按行号或 sample_id。

四种状态和退出码作为公开契约：`pass=0`、`regression=1`、`inconclusive=2`、`invalid=3`。CI 默认只允许 pass 放行，报告逐条说明阻断原因。

- 策略需先声明这是模型升级、Harness 改动还是评分迁移检查；只有指定的 manifest 字段变化被允许。模型 alias 相同但服务端身份不同需要提示，不能冒充固定版本。
- 以“candidate − baseline”的配对差区间判断。若容忍下降为 δ，区间下界 ≥ −δ 才能支持非劣；上界 < −δ 为明确回归；跨界为 inconclusive。具体区间算法复用现有实现并说明样本假设；少样本不因零差异就自动给 pass。
- env_error／API 错误单独报告和门禁，不能删去失败题后只比较幸存样本。部分分数和二元成功率明确区分。
- 题目缺失、数据／评分器变化超出声明、无法确认环境一致性、结果损坏等不能给 pass。缓存可支持质量复核，但 fresh／cached 混用不能支持推理耗时或新调用 token 成本门槛。
- 模型服务未报告版本时记录身份未知；涉及“精确模型版本回归”的策略应判 inconclusive。浮动别名可以做观测报警，不能声称精确版本因果结论。

验收覆盖四种退出码、部分分数、缺题、重复键、epoch 错配、预算与评分器意外变化、镜像漂移、缺用量、缓存、环境错误。单元测试用固定运行 fixture，无模型调用。真实版本回归结论单列待验收。

### PR-C：阶段 16，可复现工具反馈故障

首版限制在 BasicAgent 的 bash 工具结果，不覆盖模型 API、文件写入和评分器。先抽出小型、保持默认行为的工具执行包装点，再加可选策略；不要把故障状态散落进 runner。

选择三个确定性故障：指定工具调用返回“执行前暂时不可用”、执行成功但反馈丢失、反馈截断。必须区分“命令没执行”和“命令执行了但 Agent 没收到结果”，后者能暴露非幂等重试问题。

策略由样本／epoch／工具调用序号与 seed 决定，记录策略指纹、命中位置、命令是否执行、实际结果与 Agent 所见结果的独立引用。事件保存为独立 artifact；不把隐藏注入日程写入 prompt。真实长输出先按现有逻辑归档，注入输出不覆盖真实结果。

注入只作用于 Solver 工具通道；Oracle、独立评分与环境健康检查不受影响。可控故障是实验条件，底层真实 Docker 故障仍抛 `SandboxError`。改变模型所见的信息须进入 solver.describe 与 manifest，并扩展 compare 的参数分类与混杂检查；不能沿用“非预算即单机制”的宽松归因。

验收：干净条件与旧行为一致；重跑可复现；两题互不串状态；取消、故障后恢复与清理；非幂等命令在反馈丢失后被重试的真实状态可核对；评分不被注入。指标为成功率差、故障后额外调用／token、恢复步骤及二次破坏次数。恢复时间只在有可靠事件计时且全 fresh 时比较。

### PR-D：阶段 19A，Docker SRE 三题

新增 `tasks/sre.py` 与固定内容指纹的任务包，复用注册、Basic／mini／oracle 和 submission 复核流程。第一版每题单容器，前台 Agent 通过 bash 诊断服务；测试环境用轻量服务提供 logs、健康接口、固定负载探测与旁路取巧检查。

| 任务 | 初始故障 | 正确修复与独立验证 | 必须失败的取巧解 |
|---|---|---|---|
| upstream-port | 代理配置指向错误端口，服务返回失败 | 最小配置补丁；新环境启动后请求正确业务内容且上游收到请求 | 静态返回 200、关闭代理或绕过上游 |
| readiness-path | 健康检查路径配置错误，业务存在但不就绪 | 修复路径；业务与 readiness 均正常，坏请求仍保持预期错误 | 把所有请求改成 200、禁用健康检查 |
| worker-config | worker 配置错误导致固定批次任务无法完成 | 修复配置；重启后完成固定消息集，检查内容、数量与去重 | 丢弃任务、伪造完成文件、关闭检查 |

第一版名称和细节可随独立验证实现微调，但必须三类不同故障，不把三个端口数当三道新题。选择这些轻量场景是为现有单容器接口服务；DNS、OOM、证书、Kafka、真实多服务和网络策略留到后续，不声称已经覆盖。

Agent 只能提交允许路径下的配置／代码补丁。评分器在新环境重放补丁，独立注入隐藏测试数据并运行只读验证逻辑；任务指令可公开功能要求，隐藏的是测试实例和评测器材料。冻结 patch 允许路径，拒绝路径逃逸、验证器修改及服务镜像替换。

每题验证分为修复后的功能、连续窗口内健康、有限负载下的正确性和保留正常功能四项；首版二元通过要求全部达标，细项作为诊断。窗口默认可先设 10 秒、1 秒一次并写入 scorer.describe；只代表小型恢复检查，不宣称生产 SLO。记录 time-to-recovery 需用统一观测器，不能从 Agent 宣称修复的时间推定。

每题先 Oracle／no-op，再加入静态 200、禁用检查、错误配置等对抗提交。Docker 测试明确 required 镜像与资源，缺条件 skip 并注明；CI 单测使用 fake sandbox，不联网。演示最终保存补丁、服务日志、探测记录与 verify 输出。

### PR-E：阶段 11A，受约束任务工厂

先做模板实例化与质量筛选，再接 LLM 生成。输出任务候选包与 provenance，默认不注册、不合并到正式题库。

任务规格包括 family_id、template_version、seed、可见指令、初始故障参数、环境指纹、oracle、验证器版本和数据切分身份。相同规格确定性产出；同家族不同端口／名称不能被当成独立测试集。

流水线：模板渲染 → schema／内容校验 → Oracle → no-op → 错误修复／取巧变体 → 去重 → 生成审查报告。故障必需性通过移除故障后的健康基线证明；验证器有效性通过错误提交变体证明。检查命令必须在隔离环境执行。

LLM 后续只提出允许的参数或模板 diff。新增验证器与 Oracle 需独立审查，不允许同一模型出题、生成答案并独自宣布有效。难度标签依据真实 Solver 试跑与成本，未试跑则标 unknown。首版至少用 2 个家族演示家族级切分和近重复拒绝；这样的小集合只验工厂机制，不支持泛化结论。

验收：重建哈希相同；重复家族不会跨 split；Oracle 不过、no-op 能过、对抗解能过的候选都拒收；生成失败保留失败原因。LLM 生成质量另行用真实候选和独立审查评估。

### PR-F：阶段 12A，有限配置优化实验

拆两步交付，避免一次实现一个“自动进化框架”。

F1 先做离线建议：读取 PR-A 报告，按显式规则生成配置候选与理由，附证据引用。仅改变白名单内的现有 Solver 参数；首个变量选 `max_observation_chars`。如果诊断不足，输出“无候选”也有效。

F2 再做有界搜索：生成 CompareSpec，复用 compare 执行；冻结单变量候选集合、训练／验证／测试家族划分和选择规则。训练用于提案，验证用于选一个候选，测试仅做一次最终评价，不把逐题测试轨迹反馈给提案器。

现有 compare 只有单一 task，先在每个 split 的固定子集上分别执行并关联 experiment_id；不要暗中拼接不同任务结果或为此重写 CompareSpec。task fingerprint 需记录切分文件及其内容哈希。

选择策略预先声明成功率下界／不确定性与成本约束，优先返回“无明确改进”而非挑中偶然高分。记录所有候选、失败、搜索次数、提案模型用量、验证推理用量、最终测试用量与服务端身份，搜索成本与最终部署成本分开。小样本报告只作为演示。

硬限额包含候选数、调用数、wall time 与 token 软预算；当前 token_limit 最后一次调用可能超出，不能称为严格费用上限。恢复时不重复消费已完成候选，未完整运行或环境漂移的实验不得选胜者。测试一旦被用于迭代，应撤销 holdout 身份并建立新版本。

首版不自动提交代码、不改评分器／任务答案、不放宽预算获取虚假改进。若要研究重试、上下文压缩等新策略，单独实现可指纹化的 Solver 变体并做机制消融，再纳入候选空间。

## 5. 后续阶段怎样开，而不是现在全部铺开

### 19B：真实 K8s SRE

当 Docker 三题与验收链稳定后，先一题 kind 中的 Service selector 故障，再考虑 NetworkPolicy、DNS、资源限制。K8s 作为被测任务环境与阶段十七“用 K8s 调度评测”是两件事。

当前 `SandboxSpec`／`SandboxProvider` 主要是单容器，无法凭一个 Task 插件自然获得安全的多服务集群。先写独立环境能力 ADR，再增加可选 provider；不得偷偷用宿主 Docker socket 赋予 Agent 集群管理能力。Agent 凭据只作用于一次性测试环境，验证器使用独立权限；首版单租户 disposable cluster，不把 namespace 当作强安全隔离。

验收需包含故障恢复、健康工作负载不回退、越权失败、集群／凭据／网络回收和复现。通过后才扩 5～10 类任务。

### 14：长任务与记忆

先做“短时多里程碑 + 故意中断恢复”，再增加时长，不能简单把 time_limit 调到 8 小时。现有 resume 主要复用已完成样本／缓存，不等于恢复单个 Agent 中途的进程、文件和会话状态。

检查点应绑定 task／solver／环境版本、允许恢复的消息、累计预算、工件与环境恢复说明；继续执行不能重置 token／time／重试计数。区分重新执行、重建环境后恢复、原环境续跑三种语义。不做通用 Docker 内存快照，首版从持久工件重建。

比较 no-memory、固定摘要、结构化记忆时计入摘要模型成本，冻结各自策略；里程碑由独立验证器判定。指标含最终成功、里程碑保持、恢复损失、跨阶段信息保留、token 与耗时。长时间运行只是时长维度，不等于长任务能力已被证明。

### 15：多 Agent

只做一个双角色 Solver（执行者／审查者）与单 Agent 对照，不自建通用协作框架。所有子角色调用复用平台预算与调用统计；总 token、wall time、工具次数、消息与共享工件完整记录。先串行协作，后研究并行。

角色通信开销、审查收益、错误建议传播和共享文件冲突均需可定位。固定任务与总预算政策；并发使时间口径不同，应单列分析。不能给两个 Agent 各一份完整预算后声称协作机制带来收益。

### 17：调度

只有出现实际单机排队／任务恢复需求才开工。第一步本机 SQLite 队列＋多进程 worker，复用一次普通 run 的执行路径；runner 不承担队列控制面。

状态机需有 pending／leased／running／completed／failed／cancelled；租约、心跳、尝试号、幂等提交标识与不可变产物目录分开。分布式默认至少一次执行，不承诺恰好一次；过期 worker 返回结果不能覆盖新有效结果。SQLite 队列不放跨主机共享文件系统，跨主机再换具备事务租约的存储或现成队列。

验收覆盖 kill worker、失联恢复、重复提交、迟到结果、取消竞态、磁盘不足与清理。到这一步再按实际瓶颈选择 K8s Jobs，而非预先建设集群。

### 20：结果体验与 CI／公开榜

先从归档生成本地静态 HTML：筛选任务／模型／outcome，展示步骤与证据、回归报告和版本信息。输出完全转义日志、prompt 和模型文本，禁止执行模型生成的 HTML／脚本；artifacts 只允许访问报告根内的文件。无需新增在线数据库或 Web 服务。

CI 先跑现有测试和离线回归 fixture，真实模型运行配置为手动／独立端点预算。报告作为 CI 工件供审查，不默认向外发布原始轨迹。公开榜另设数据许可、凭据与私有材料检查，以及版本／预算／样本范围／误差展示，获得明确发布授权后再上线。

## 8. 每轮统一验收

1. 新行为有命令或小型 demo，接口／schema／默认值写进文档；所有新评分或模型可见变化进入 describe 指纹。
2. 单元测试不需要网络／API；Docker 集成明确实测或 skipped；真实模型实验单独记录端点身份、任务版本、预算政策、调用与原始产物。
3. 新终端／SRE 任务必须 Oracle 通过、no-op 失败，再补至少一种绕过验证的反例。
4. 对照声明允许变化、数据切分和不确定性；不同机制／预算／环境不能混为因果收益。
5. 每轮中文 progress、索引和路线图更新；实现／模拟测试／环境验收／真实研究结论分别标记。
6. 本轮通过后再开下一批。发现原有阻塞问题时先最小修复，保留本轮未完成项，不将其标成完成。
