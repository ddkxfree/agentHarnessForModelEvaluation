# Harbor 双执行入口开发指南（交给 Cursor／Opus）

日期：2026-11-03。性质：用户确认方向后的开发交接。**本文是待实现方案，不表示 Harbor 已安装、集成或验收。**

## 1. 目标与起点

在现有平台旁增加隔离的 Harbor 调用入口：同仓库、不同执行模块和依赖环境、统一只读结果分析。Harbor 使用固定版本的正式发行包，通过独立进程调用；不复制其源码进本仓库，不 fork，不把 Harbor 当成自研 Solver。

```text
实验配置、归档、比较、统计、诊断
               │
     ┌─────────┴──────────┐
现有 Native 执行器      Harbor CLI 适配层
core / Solver / Docker  独立进程与固定依赖环境
     └─────────┬──────────┘
        带来源的统一结果视图
        保留各自原始证据
```

文档基准 master `9d828e4`，开始开发时以实际最新 master 为准并记录 SHA。现有 CLI 是 `src/harness/cli.py`，原生结果为 manifest／JSONL／artifacts；compare 内部直接调用 run_eval，不是现成的后端无关调度器。

已经有 Terminal-Bench 2.0 的 5 题适配，但没有 Harbor 执行后端。用户已实际完成 fix-git 参考解及 DeepSeek＋BasicAgent 单题实验；这些记录是 Native 来源，不得重新标记成 Harbor。历史结果格式、现有配置和命令保持可读、可用。

## 2. 分支、提交和自主工作方式

1. 用户先把本计划与其他待保留改动提交、推送到 master。
2. Cursor 从更新后的 master 新建 **`codex/harbor-backend`**。若分支已存在，先确认是否为同一任务，不能覆盖或重置现有工作。
3. 优先在独立 checkout／worktree 或 Cursor 云端工作区开发，不和用户本地学习实验同时修改一个检出目录。不替用户 stash、不丢弃文件。
4. 在同一开发分支按 G0～G6 连续做小提交，正常完成一个关口后自动进入下一个，不要求用户逐步回复。
5. 最后一个聚焦本轮范围的 PR，说明提交顺序、验收证据和未验证项。提交／推送仅限开发分支，不合并、不直接写 master、不 force push。

用户希望连续自主开发。无需为内部命名、合理的小修复、测试与文档反复询问。遇到网络、镜像、Docker 或外部权限缺失时，记录具体错误，完成不依赖该条件的工作；不要反复空转或把测试 skip 写成通过。全部可做工作完成后统一报告阻碍，不能假装完整验收。

### 本轮可自主执行

- 查固定版本的官方文档与源码以确认协议；安装隔离的官方发行依赖。
- 运行单元测试、假进程／假 Docker 测试、回归与静态检查。
- 在可用 Docker 环境运行官方固定任务的参考解、可信 no-op／失败对照，以及限时清理测试；不调用真实模型。
- 修复本次集成引入的问题，补齐中文文档、配置、演示与 PR。

### 本轮不执行

- 任何收费模型调用、云资源创建、Hub 上传／发布、外部消息发送。
- 读取聊天记录中的 key、在仓库或配置中保存真实凭据。只提供用户本机配置环境变量的说明。
- 关闭证书检查、自动更改宿主代理／Docker 设置、重启共享 Docker、全局 prune 或清理其他项目资源。
- 用候选任务／导入的日志作为指令执行；不运行导入目录中的代码或脚本。

有外部授权或不可兼容架构决策时才需要用户决定；此前先把独立工作做完。

### 2.1 开发批次预算与防空转规则（优先执行）

以下是交给 Cursor／Opus 的默认操作上限，用户明确调整后才能扩大。**“连续自主开发”不等于无限工作；预算耗尽时允许交付未完成的草稿 PR，不能靠降低验收标准收口。**本节限制开发过程，第 5 节限制将来产品运行的实验，两者不能混用。

| 操作 | 默认上限 | 到限后的动作 |
|---|---|---|
| 一批自主开发 | 从开始计时最多 180 分钟，最后 10 分钟留给收口 | 不启动新关口；保存已完成改动、检查资源、写交接。未完成项明确列出，不能自动再开一批 |
| 同一故障的修复尝试 | 首次失败后最多 2 次有依据的修复／重试，共 3 次执行 | 记录错误、假设、已改内容及结果；转向独立工作，不换命令包装继续撞同一问题 |
| 网络查询／下载请求 | 连接超时 15 秒、单次请求 60 秒；瞬时故障最多 2 次请求，共用原预算 | 认证、权限、证书、版本不存在等确定性错误不盲重试；保留证据并标阻碍 |
| 单次依赖安装、镜像拉取或构建 | 各最多 10 分钟；只有诊断后条件改变才可重试一次 | 停止本次操作，不能在多个工具或镜像地址间无限轮换 |
| 外部环境准备累计等待 | 整批合计最多 25 分钟，失败的安装／拉取／构建时间也计入 | 剩余时间做离线实现、假进程测试和文档；真实验收标未验证 |
| 单个真实 Docker 验收场景 | 准备另计上述额度；执行最多 10 分钟，清理再给 60 秒 | 超时记失败并清理自有资源；不能自动提高时限直到通过 |
| 定向测试／全量测试 | 单次分别最多 5／15 分钟 | 先查停在哪个用例；复现只跑相关用例，按同一故障次数收口 |
| 长任务观察 | 每 30～60 秒检查一次；单次工具等待不超过 60 秒 | 有输出只取增量；无输出按原截止时间处理，不能因有进度就重置截止时间 |
| 单个接口的资料查证 | 最多 15 分钟，优先固定发行版官方文档与源码 | 还不能确认就记录未知；不靠猜测制造兼容接口或“真实”样例 |

上限取最先触发者。父任务、子进程、库内重试共用总截止时间；不得外层 3 次、内层又 3 次放大尝试数。测试超时不能写为通过，取消后的清理失败必须报告剩余资源。若既有测试确实正常需要更久，保存基线证据并留待下一批调整，不在本批悄悄无限延长。

### 2.2 计时、进程退出和上下文恢复

开始时建立本地工作账本，例如被 Git 忽略的 `runs/harbor-dev-session/progress.json`：记录开始时间、总截止时间、当前关口、环境等待累计值、各故障尝试次数、最后错误、日志路径和本批创建的资源身份。进度记录不含凭据。账本不是产品新功能，不要为了它再开发一套调度系统。

- 用实际时间记录已消耗预算；上下文压缩、重新读取任务或 Agent 自动续跑不重置截止时间与尝试次数。用户明确开始下一批后才建立新的批次。
- 每个可能挂起的命令在启动前有截止时间和退出方案。使用当前平台可用的进程超时／看门狗；不能假定 macOS 自带 GNU `timeout`。仅让工具调用提前返回、得到后台 session ID，不代表底层进程已受限。
- 超时先向已确认归属的进程组请求退出，10 秒后仍在运行则终止；这段时间包含在 60 秒清理窗口内。容器按本 Job 的 ID／标签清理，不能只杀 CLI 就认定容器消失。禁止杀其他开发或用户实验进程。
- 停止重试、进入离线工作前，先确认失败操作不再后台运行。无法证明归属时不要扩大杀进程范围；记录残留身份与清理失败，停止依赖该资源的验收。
- 正常开发每完成一个关口更新账本；长关口至少每 30 分钟落一次检查点。会话支持进度消息时简要说明已完成和下一步，不要求用户中途回复，也不发送无变化的重复状态。

### 2.3 控制输出、重复检查和 token 消耗

1. 先用 `rg` 定位、按需读文件和 diff，不反复扫描整个仓库、打印 lockfile 或重复读取已确认的长文档。工具输出默认不超过约 80 行／8 KB；完整日志写文件，失败时读取有关片段，不能截掉失败判断依据。
2. 先跑受影响的定向测试，再在 PR 收口前跑一次全量测试与静态检查。已经通过且代码／环境未变化的检查不重复；新修改影响范围或新失败能说明理由时才重跑。
3. 不同时启动多个竞争镜像、依赖或同一验收环境的任务。已安装的固定依赖、已验证镜像和本批日志优先复用，不为得到更好看的耗时反复重跑。
4. 没有新增证据时，不反复改写计划、自我评审或让另一个 Agent 重做同一分析。此交接默认单 Agent 实现，不自行扩成多 Agent 竞赛。
5. 不能可靠获得 Cursor 开发模型的实际 token 消耗时，就写“开发用量未知”，不编造数值。**本文无法设置 Cursor 的账户硬限额，也无法保证模型一定遵守；限制要靠执行时的命令超时、工作账本和 Agent 遵循指令落实。**180 分钟同样是会话停止规则，除非执行环境提供外部控制，否则不是自动强制关闭 Cursor 的计时器。实验中的 token_limit 不限制 Cursor 开发额度。

### 2.4 必须收口的情形与交付格式

同一阻碍耗尽重试、环境等待到限、总时限剩余 10 分钟、需要收费／外部权限，或发现无法在本批解决的原有功能回归时，停止相应依赖链。尚有预算就完成独立工作；预算到限则保存现场并结束本批，不无限等待用户、继续轮询或擅自开启下一批。

最终统一交付：已完成关口及提交、实际通过／失败／跳过／未运行的检查、耗时和尝试摘要、遗留资源与风险、下一批第一条可执行动作。有未完成项则 PR 标为草稿或明确不可合并；无法推送／建 PR 时保留本地提交并说明原因，不能因此无限重试。**G0～G6 是功能验收顺序，不承诺一个 180 分钟批次全部完成；预算规则优先，未通过的关口仍是未完成。**

## 3. 本次范围与命令契约

**保留 `harness run` 为 Native 入口，新增独立 `harness harbor` 命令组。**第一版不强制重命名成 `harness native run`，不大规模重构 cli.py。

拟定命令（当前均未实现）：

```text
harness harbor doctor [--config FILE]
harness harbor run -c FILE
harness harbor import JOB_DIR
harness harbor status RUN_DIR
harness harbor cancel RUN_DIR
harness harbor resume RUN_DIR

harness show RUN_DIR [--sample ID]
harness diff RUN_A RUN_B
harness report RUN_DIR
```

- doctor 默认只做环境／版本／配置预检，不发模型请求、不自动下载大镜像、不输出凭据。
- run 为本地前台执行；启动前打印执行器、任务数量、Agent／模型、实际限制及原生目录。用户主动运行真实 Agent 时可正常消费其配置的端点，本轮开发验收只用参考解和假模型。
- import 纯离线，不需要安装 Harbor、Docker 或 key，不改变源 Job。可重复导入且不重复计数；不同解析版本应可追踪重建。
- status 能跨本平台 CLI 进程读取归档状态；不得仅凭 PID 存在判断是本次任务。
- cancel 只能针对本次可证明归属的进程、Job 和资源；本机进程控制信息与可分享 manifest 分开，不能根据导入文件任意杀 PID。
- resume 使用锁定版本的 Harbor 原生恢复语义；不是我们 Native 的模型请求缓存回放。已完成任务不重复计分，重试与独立重复不混淆。
- show／diff／report 保留旧格式兼容，通过统一读取层识别来源。两种格式混合读取也不能触发执行或模型请求。

本次不改 `harness compare` 的 Native 执行编排。**先支持已经归档的跨来源结果分析，自动跨引擎矩阵调度留到后续。**不要让 compare 的现有配置看起来能驱动 Harbor，实际却被忽略。

首版只运行：本地 Docker、固定 fix-git 任务、Oracle 和开发用可信失败对照；为一个经过测试的 Harbor Agent 保留真实模型配置示例，但标注真实请求未验收。

## 4. 模块与依赖边界

建议新增：

```text
src/harness/harbor_cli.py             薄 Typer 命令组
src/harness/integrations/harbor/
    config.py                       集成配置与能力校验
    runtime.py                      独立发行环境和 CLI 身份
    process.py                      执行、状态、取消、恢复
    importer.py                     Harbor 结果读取与归档
    mapping.py                      原生结果到共享视图
src/harness/results/                来源、可空指标、只读视图与分发
configs/harbor/                      参考解与真实 Agent 示例分开
tests/fixtures/harbor/               小型、脱敏、注明版本的结果样例
```

可按实际接口调整内部文件名，边界不变。不要同时创建 cli.py 和同名 cli 包造成入口歧义。core/runner.py、现有 Solver／DockerProvider 不导入 Harbor；Harbor 入口不通过 run_eval 外包一遍已由 Harbor 管理的 Trial。

Harbor 在独立虚拟环境或 uv tool 环境安装；记录确切版本、Python、安装入口及依赖锁／安装收据。不可把未锁定 `uvx harbor` 当成固定依赖。对用户提供的 CLI 路径验证版本与能力，不静默切换 PATH 上另一个版本。

本轮不预写猜测的版本号：**G0 必须选择一个实际存在、可安装的正式版本，并把准确 pin、发行来源、已验证 CLI 参数和解析样例写入仓库。**此后实现、样例、验收都针对该版本；其他版本默认明确拒绝，不能仅报警后继续误解析。无 Harbor 的基础安装仍可 run Native、show 旧结果和 import 离线结果。

## 5. 配置、身份和限制

集成配置包含 schema_version、Harbor 版本／可执行文件选择、精确任务来源、Agent／模型配置、环境、并发、重复与原生超时策略。具体字段在 G0 对照选中版本落地，不复制一整套可能漂移的 JobConfig 到现有 RunConfig。

原生 Harbor 配置可作为经验证的配置文件保留，不做任意 shell 字符串拼接或隐式任意参数透传。记录“请求的配置”和“解析后的实际配置”，相对路径按明确的配置基准解析，不依赖偶然 cwd。

- Dataset 名称／版本不是唯一身份：记录解析出的任务列表、来源提交／内容指纹、镜像 digest／平台。若无法记录某项，显示未知并降低可比性，不能用 tag 冒充 digest。
- 示例任务优先复用项目固定提交 `2fd12b88aafdd04a52c298e3940bcb189f9766d6` 中的 fix-git 及既有镜像 digest；若锁定 Harbor 不支持直接采用该镜像，先证明等价方式，否则标记环境差异，不宣称引擎严格对照。
- 模型名称、Agent 版本、提示配置、采样参数、工具与上下文策略必须可追踪；不能只记录 deepseek-flash 字符串就称身份完全固定。
- 凭据经必要的环境变量／原生认证机制传递，不放 argv、YAML、manifest 或测试样例。只转交执行所需环境，同时保留经过审查的 Docker／证书／网络配置需求。
- 展示能力表：哪些限制可执行、哪些仅事后统计、哪些不支持。用户要求的 token／费用／步数限制不能实现时，启动前报错，不能静默忽略。
- 阶段时间分开：准备、排队、Agent、验证、清理、总耗时。超时边界、重试、重复归属明确；不得外层内层同时执行同义重试或重复。

## 6. 结果契约与分析

先实现 backend-aware 的只读 RunView／SampleView（具体命名可调整）。Native 通过适配现有 SampleResult 读取；Harbor 保留原生数据，通过 mapping 提供共享字段。**不为了复用 classify() 强造 output、零 token 或假的模型步骤。**

必须能表示：

| 维度 | 要求 |
|---|---|
| 来源 | backend、版本、导入器版本、原生 Job／Trial ID、原始路径与哈希 |
| 样本身份 | 任务来源和版本、原生名称、稳定平台 ID、独立重复编号、重试编号 |
| 运行状态 | running／completed／cancelled／interrupted／invalid 等，与任务得分分离 |
| 评分 | 原始 reward／多指标、是否有效、验证器身份；首版已知二元分数可形成 correct／wrong |
| 异常 | 原生异常、阶段、平台映射；未知异常保留 unknown，不统一写 api_error |
| 用量 | input／output／cache／费用及来源，缺失为 null／unknown；展示覆盖率 |
| 轨迹 | 原始 Agent 日志和可用 ATIF；没有标准轨迹时如实显示，不虚构模型消息 |
| 产物 | 原始文件索引、大小、哈希；缺少文件、修改或采集中断可检测 |

多 reward／部分得分在首版没有适用聚合规则时，保留原始值并标记暂不支持该统计，不能任取第一个指标或把所有 reward>0 当成功。未知样本不从分母无声消失。Oracle 的零模型调用与“真实 Agent 没报告用量”必须区分。

原始 Job 目录或独立快照保留；标准化视图可重建，不能覆盖原生记录或改变已有 Native 文件。输出放 runs 下独立 Harbor 运行目录并标记来源。源文件运行中变化时，不生成声称完整的快照；同源不同内容／导入器版本的重复导入有明确策略。

导入把文件当数据：防目录穿越／符号链接越界，不执行配置中的 import path，不渲染外来 HTML／终端控制序列；未知 schema 版本明确拒绝或标记不兼容。日志不可信，控制台用安全文本展示。

原始证据保留以不泄露凭据为前提：源配置避免写入密钥；若发现认证字段，导入归档应脱敏并记录处理，不能将秘密写入可分享目录。不要把未经审查的原始运行作为公开 PR 工件。

diff／report 至少区分分数可比性与成本可比性。相同名称但任务指纹不同不能当同题；不同 Agent／后端配置可展示系统对照，但不能归因成纯引擎差异。时间范围、缓存、重试口径不同要提示；小样本照旧输出不确定性，不宣称显著胜出。

## 7. 生命周期与资源所有权

- 本平台跟踪 Harbor 进程，Harbor 管理其任务资源；不要再为同一 Trial 创建 Native sandbox 或重复评分。
- 配置检查、准备、创建／启动、执行、验证、取消／清理均有可解释的截止时间，不能仅限模型阶段。可用独立准备预算，但须记录并说明是否计入总耗时。
- 使用 argv 列表、独立工作目录／进程组，持久化状态和启动身份；持续落盘已有结果。日志量／磁盘使用有上限策略，不能无界缓冲到内存。
- 验证锁定 Harbor 的中断行为，不假定杀 CLI 就一定清理完容器或取消服务端请求。取消已发出的请求也不保证免除费用。
- 覆盖取消前启动、创建／启动中取消、创建结果迟到、准备超时、中途退出等场景。操作限定本次可证明归属的资源，迟到创建也要处理。
- 进程重启后 cancel／resume 先验证 Job 身份和进程身份，防 PID 复用；恢复有互斥，避免两个 CLI 同时重复执行。
- 记录取消请求、已结束和清理失败；任务已得分但清理失败不能隐藏。归属不能确定时报告而非广泛删除。
- Job 退出码 0 不等于每道题成功，非零也不等于没有有效 Trial；以逐 Trial 原始记录判断，保留部分完成结果。

## 8. 连续开发关口与提交建议

| 关口 | 交付／建议提交 | 自验与进入下一步的条件 |
|---|---|---|
| G0 契约与预检 | 固定版本、依赖隔离、配置与能力表、doctor | 官方版本可核查；有／无 Harbor、版本错、缺 Docker 等准确提示；明确兼容样例 |
| G1 离线导入 | importer、脱敏 fixtures、来源视图 | 有效／无效／部分结果、缺用量、缺轨迹、多 reward、文件变化、路径越界、重复导入用例通过；无网络／Docker可运行 |
| G2 共享展示 | show／diff／report 的来源读取 | 旧 Native 结果兼容；真实导入原生值对齐；unknown 不变 0；不兼容实验不被当严格对照 |
| G3 统一启动 | harbor run、配置收据、日志与状态 | 假 CLI 覆盖启动失败、部分成功、异常退出；无秘密泄露；未支持参数启动前拒绝 |
| G4 取消与恢复 | status／cancel／resume、持久状态 | 假进程覆盖取消交接、迟到资源、重启、重复恢复、清理失败；不影响其他 Job；已有结果保留 |
| G5 真实无模型 | 官方 fix-git Oracle＋可信失败对照、实际取消测试 | 本地 Docker／锁定 Harbor 真正执行；原生分数与导入值一致；无遗留本次资源；过程与限制记录 |
| G6 收口 | 上手文档、演示、完整回归、PR | 基础无 Harbor 安装仍可用；lint／format／测试通过；完成／未验证分开；不启动新的收费实验 |

G0 先核查结构，G1／G2 可先用锁定发行版的脱敏样例完成，再接管执行；不能猜格式写完后再找版本。每关验证后连续推进，开发过程中发现问题在本范围内自主补修，不逐步打扰用户。

若真实环境缺失，G5 可记为 blocked／未验证，继续完成 G6 的离线部分与可复现命令，最终提交 draft PR 或明确未完成的 PR 描述。不能把代码回归通过写成“Harbor 真正运行通过”。
