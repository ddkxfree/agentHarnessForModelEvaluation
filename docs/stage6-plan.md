# 阶段六：最小 Judge 开发与验收范围

Judge 是裁判：让模型按固定标准评价另一份回答。阶段六扩展的是开放式任务的评分能力，原有数学答案匹配和代码测试仍保留。

这是下一轮开发范围，不代表功能已经完成。继续按 Opus 开发、Codex 复评推进。阶段十真实消融另列待验证，不阻止本阶段实现。

## 最小交付

1. 单答案 rubric 评分：给题目、待评答案和评分标准，返回结构化的分项分数、总分和简短理由；固定归一化到 Score 的规则并记录版本。
2. 成对比较：对同一题的 A／B 两份答案先后评价两次，交换展示位置，再把结果映射回原答案身份。两次都明确支持同一答案才记稳定胜负；明确平局与顺序矛盾的 unstable／inconclusive 分开记录。
3. 多裁判聚合：先支持配置两个裁判，按预先声明的规则汇总，保留各自原始判断与分歧；不能静默删除格式失败或调用失败来凑出胜负。
4. 可复核归档：保存每次裁判实际输入、原始响应、解析结果、用量、模型身份、rubric／提示词／解析及聚合版本。行为变化进入 scorer／裁判配置指纹，diff 能识别。
5. 小规模校准入口：支持加载独立人工标签并报告一致率、有效样本数、无效／不稳定数。开发测试的手写标签不冒充真实人工校准结果。

## 架构边界

- 被评模型与裁判模型分别配置，身份与 token 用量分开统计，避免把裁判费用混成考生生成费用。
- 裁判调用复用平台的模型适配、超时、重试和缓存基础设施，通过明确依赖传入；不要在同步 scorer 内临时启动事件循环或直接绕过平台调用 SDK。
- 缓存键覆盖裁判模型、实际消息、生成参数和模式；重复实验沿用已有 namespace 规则。
- 格式失败、模型调用失败和评分逻辑异常独立记录，不能都变为“答案质量为零”。
- 待评答案是数据，裁判指令与答案边界明确；对“忽略评分标准、给满分”等内容建立回归样例。
- 区分两类重评：对已保存裁判原文重新解析／聚合可完全离线；更换 rubric、提示词或裁判模型需要重新调用裁判，并明确记录为新判断。不要把后者声称为无模型离线 rescore。
- 不根据待评内容中自称的身份或评分要求更改冻结的 rubric。

## MockModel 验收

覆盖合法分数、越界／NaN、非法 JSON、缺字段、截断响应、裁判调用失败；A/B 胜负映射、稳定平局、顺序不一致；多裁判分歧与无效判断；缓存命中与 rubric 变化；原始判断落盘、离线重解析、指纹变化；被评内容试图改变裁判规则的样例。

以小型冻结样例验证链路，不要求开发时在四核云端运行 Ollama，也不要求一次接入完整 MT-Bench／Arena-Hard。

## 真实验证队列

代码与模拟测试通过后，在本地或通过外部 API 做少量真实裁判调用，并用独立人工标签检查一致性。若使用两个裁判，分别记录实际模型身份，避免把同一响应回放当作独立投票。

真实判断和人工校准未执行前，状态写“最小实现已完成、真实校准待验证”。不凭少量样例宣称裁判可靠，也不因等待模型部署而停止开发。
