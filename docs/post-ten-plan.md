## 建议：先开始使用，同时继续有边界的开发

不要等全部功能与扩展完成后才第一次使用，也不要为消耗额度不断重构。分两条线：用户与 Codex 在本地完成小规模试跑和理解；Opus 在独立开发分支完成阶段八及操作体验补充。试跑产生的问题进入后续开发验收，不随意扩大核心接口。

## A 线：跑通并理解已有系统

按依赖从少到多推进，先一次重复，确认链路后才扩样本和轮次。

| 步骤 | 内容 | 验收产物 |
|---|---|---|
| A1 环境检查 | 确认代码版本、依赖、Docker 连接、容器架构、模型端点与工具调用能力 | 环境清单；缺失条件明确记录，不能把跳过当通过 |
| A2 无模型校验 | 三个自建终端任务的 Oracle／不操作对照 | 正反例结果、评分与容器清理记录 |
| A3 第一次真实调用 | 问答小样本、一题终端任务；检查 prompt、tool_calls、输出和得分 | 一个能逐步解释的完整运行目录 |
| A4 实验工具 | 同一小集合执行 diff、report、重复运行与中断恢复 | 缓存与新调用区别、失败报告、恢复记录 |
| A5 真实任务 | TB 选一两题，SWE 选一题先做 Oracle，再跑 Solver；SWE verify | 实际模型与环境结果、产物哈希、独立复核 |
| A6 新能力 | 一次真实单变量消融、小型 Judge 校准、一个真实接入尝试 | 配置、输入版本、结果路径、已验证与未验证清单 |

不能用模型分数高低代替链路验收。小样本不做排行榜或显著性结论。Judge 人工标签需独立于裁判本身，真实自动接入需独立正反例和人工评审候选 diff。

## B 线：Opus 的开发队列

### B1 完成已有承诺

- 阶段六 J1／J2 代码回归已通过；安排真实 Judge 校准，不再作为待开发补修。
- 阶段八最小工作流和取消补修已通过本轮相关回归；安排 Docker 环境复核与真实模型接入，不再作为尚未实现阶段。
- 统一路线图状态：实现完成、MockModel 测试、真实验收分开；旧评审基准作为历史，不再描述为当前提交。

### B2 上手与运行工具

开发环境预检入口（命令名由实现决定），默认不发收费模型请求：检查依赖、Docker、平台与镜像架构、所需凭据是否配置；只输出凭据是否存在，不输出密钥。需要模型实际调用的探测应明确区分并可单独执行。

补小规模 smoke 配置与结果检查脚本，保留既有 CLI，明确预期行为：Oracle 通过、错误解失败、产物存在、容器清理、缓存／真实调用计数合理。不要要求模型必须达到某个预设准确率才算流程可用。

修订 hands-on：当前仍含旧的 announce 仓库地址与旧开发分支；改成当前项目的实际地址与稳定提交／分支，覆盖新增 TB、compare、Judge 命令。命令应经过可用环境验证，缺条件的标注未验证；不复制旧模型分数当作运行保证。

交付一份短演示脚本：从一个任务出发讲清 Task → Solver → 模型 → 工具 → Scorer → manifest／轨迹 → diff。它既帮助用户理解，也可作为后续项目展示材料。

### B3 结果查看，再考虑存储与调度

先实现本地只读的结果浏览与导出：读取现有 manifest／JSONL，查看按任务与失败类型筛选、轨迹、产物、模型版本、比较结果、裁判分歧与调用用量。不要同时重写 runner、存储格式和调度器。

如结果数量使查询明显不便，再增加可重建的 SQLite 索引，原始归档保留为事实来源。没有实际排队和资源冲突证据前，不优先引入 Ray／Kubernetes。

## 有意义的后续扩展顺序

1. 现有十阶段的操作体验和真实验收：优先级最高。
2. 外部 Agent 接入或一次独立 GPU 推理部署实验：选一个做深，复用现有接口；先明确能回答的工程问题与验收证据。
3. 服务化任务队列、持久化状态和资源调度：先单机可恢复，再按实际规模考虑分布式。
4. 新任务范式：工具调用／多轮交互、多模态等，每次增加一种验证抽象，避免只堆评测集名称。

这些不是到期前必须全部开发的承诺。GPU 租赁应在脚本、数据和指标准备好后决定；先测本地或 API 小运行的速度、模型兼容性与实际用量，避免租卡时间耗在配置和调试上。

## 每个开发批次的交付要求

- 明确用户可观察的新行为，提供可运行命令或演示。
- 适当的回归测试、中文进度记录、可单独评审的 PR。
- 说明真实数据／模型是否运行过，保留证据路径。
- 多个开发任务放在独立分支与检出目录，避免同时修改相同核心文件。
- 本轮验收后冻结一份可玩的基线，后续改进不得让已有演示回退。

目标是把 Cursor 开发额度转化为可维护、可演示的交付物，而非以消耗额度或功能数量作为进度指标。
