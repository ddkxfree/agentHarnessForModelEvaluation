## 阶段七：让比较结果有统计依据

解决的问题：模型一次答对，可能只是碰巧；一次失败，也可能是环境出了问题。

做法：同一批题重复运行，分清缓存重放与新推理；计算逐题配对差、波动和置信区间；抽取失败样本生成报告。

你能做的事：查看“哪几题反复失败、差多少、结果是否稳定”，不只看一个准确率。

实现说明：[13](progress/13-statistics-diagnostics.md)；补修说明：[15](progress/15-stage7-review-fixes.md)。

## 阶段十：固定模型，研究 Harness 的作用

解决的问题：成绩变化来自模型，还是提示词、工具协议、观察截断和执行预算？

例子：同一模型、同一批题、同样步数和 token 预算，只把命令输出从保留 4000 字符改为 500 字符，看表现怎样变化。这是机制消融。

如果只把 token 预算从 40000 改成 8000，是预算敏感性实验。如果把 BasicAgent 换成 mini-swe-agent，是整个 Agent 的对照。三种实验应分开解释。

你能做的事：运行对照配置，比较成功率、调用成本、耗时和轨迹，解释某个机制在哪些题上有帮助。

阶段十实现分支有 `docs/progress/16-budget-ablation.md`；本文所在工作区未必已切换到该分支。评审见 [17](progress/17-stage10-review.md)。真实单变量消融仍需实际运行，不能只凭单元测试标为完成。

## 阶段六：让模型当裁判，并检查裁判是否可靠

解决的问题：写作、解释、摘要等任务没有简单标准答案，不能只用字符串匹配或测试脚本判分。

最小功能：按固定评分标准打分；比较 A、B 两个答案并交换顺序；汇总多个裁判的结果；与一小批独立人工标签对照。

例子：两个模型各写一份故障分析，让裁判按准确性、证据和可执行性打分；交换 A/B 顺序，看裁判是否偏向先出现的答案。顺序不一致应记录为不稳定，不能直接等同质量相同。

你能做的事：查看每个分数依据的 rubric、原始裁判回答和分歧。需要保证换裁判／换标准的变化可追溯。

目前主要是路线图和最小验收要求，尚没有独立的已完成阶段六进度报告。

## 阶段八：让 Agent 辅助接入新评测集

解决的问题：每接一个新数据集都要手写加载、环境和判分适配，重复工作多，也容易出错。

最小功能：Agent 阅读固定版本的任务说明与样例，生成一个 Task adapter 的待评审 diff；运行独立冻结的正反例，由人评审后接入。

例子：给 Agent 一个新代码任务集的说明，它生成 `tasks/<name>.py` 和相应测试；用已知正确解与错误解验证。不能通过修改标准答案或官方评分规则让结果看起来更好。

你能做的事：从“人工从头接入”变成“Agent 产出候选实现，人做独立审查”。平台负责辅助工作，并不自动保证适配正确。

目前主要是路线图和最小验收要求，尚没有独立的已完成阶段八进度报告。

## 阶段九：复用真实评测集和第三方 Agent

负责把 SWE-bench、Terminal-Bench 和 mini-swe-agent 放进相同平台，保留官方评分流程与版本信息，并明确偏差。

它已提前穿插到第五阶段开发，不需要重新做一套重复框架。后续主要补真实运行验收和更多任务类型。

阅读：[SWE-bench 与 mini-swe-agent](progress/03-swebench-mini-swe-agent.md)、[独立复核](progress/08-independent-verification.md)、[真实 Terminal-Bench](progress/09-terminal-bench.md)。

## 哪些需要运行真实模型

开发和回归测试大多可用 MockModel、FakeProvider 及已有运行记录。阶段十真实消融、阶段六裁判效果、阶段八真实生成适配器，需要本地模型或外部模型 API 做最终验收。

无需在 Cursor 云端四核 VM 中部署大模型。云端继续开发和自动测试；本地或 API 负责小规模真实实验。功能实现、模拟测试通过、真实实验验收三种状态应分别记录。
